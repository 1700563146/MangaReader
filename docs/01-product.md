# 01 产品定位

## 一句话

**MangaReader 是「阅读器 + 规则引擎」：不搬内容，只搬阅读体验。**

## 1. 背景与问题

Android 上的漫画阅读长期存在三组矛盾：

| 矛盾 | 现状 | 后果 |
| --- | --- | --- |
| 内容与工具耦合 | 多数「漫画 App」内置站点解析，本质是内容分发 | 版权风险高、随站点变动频繁失效、下架即死 |
| 规则与代码耦合 | Cimoc 每个源继承 `MangaParser`、注册进 `SourceManager` 的 `switch`，新增源要发版 | 源的生命周期远短于 App，维护成本被转嫁到开发者 |
| 体验与格式耦合 | 在线阅读器不支持本地文件，本地阅读器交互粗糙 | 用户被迫装两三个 App |

Cimoc 在 2016–2021 年验证了「双阅读模式 + 多源解析 + 下载/本地」这套产品形态确实好用，但它的源是硬编码 Java 类：每个源 200–400 行，站点一改就等发版。MangaReader 要做的是把这件事**从「改代码」变成「改数据」**。

## 2. 目标与非目标

### 2.1 目标（v1.0 必须达成）

1. **零内置源**：安装包内不含任何具体站点的解析规则或域名。
2. **规则即插件**：社区用 JSON（必要时 + 受限 JS）扩展源，用户导入即用，无需等发版。
3. **一个内核两种阅读**：翻页（含双页）与条漫共用同一套图片流水线、进度与预取。
4. **本地优先**：全功能离线可用；书架/历史/进度/下载不依赖任何服务器。
5. **可维护**：源失效可被健康度系统识别并按优先级提示，规则可远程撤销。

### 2.2 非目标（v1.0 明确不做）

| 不做 | 原因 |
| --- | --- |
| 内置/运营漫画内容、源站点推荐位 | 直接触碰版权与内容审核责任，违背项目定位 |
| 账号、云书库、社交、评论 | 引入服务端即引入合规与成本；本地优先是卖点 |
| 绕过登录/付费/DRM 的解析 | 违法风险，且把项目从「工具」变成「破解器」 |
| 应用商店上架 | 各大商店对「可访问盗版内容」的判定极严；仅 GitHub Releases 分发 |
| 自建爬虫服务器/代理池 | 等于自建内容分发，且成本不可持续 |
| 自动静默安装更新 | 需 `REQUEST_INSTALL_PACKAGES`，风险与体验都不划算 |

## 3. 目标用户

| 画像 | 描述 | 核心诉求 | 关键场景 |
| --- | --- | --- | --- |
| **重度追更党** | 同时追 10–30 部，跨 3–5 个站点 | 一键检查更新、批量下载、跨源快速切换 | 通勤路上离线看已下载章节 |
| **本地收藏者** | 已有 NAS/网盘里的 ZIP/CBZ/图片目录 | 好用的本地阅读、进度、标签 | 平板或墨水屏阅读已归档资源 |
| **折腾型用户 / 规则作者** | 会写 XPath/CSS，愿意为社区贡献源 | 规则可调试、可热更新、报错清晰 | 站点改版后 10 分钟内提交修复规则 |
| **隐私敏感者** | 拒绝账号与遥测 | 无账号、无分析 SDK、可关网络 | 飞行模式下读本地库 |

反画像：想「打开即看、不想配置任何东西」的纯小白。我们不做内置源，首次使用需要导入规则——这是定位的代价，通过「一键导入社区规则索引」降低门槛（仍在法律边界内：索引由用户主动添加，应用不预置）。

## 4. 价值主张与差异

| 维度 | Cimoc | Tachiyomi/Mihon | Kotatsu | **MangaReader** |
| --- | --- | --- | --- | --- |
| 源形态 | 硬编码 Java 类，随包发版 | 扩展 APK（Kotlin/JAR） | 内置/远程解析器 | **JSON 规则 + 受限 JS，热更新** |
| 新增源成本 | 改 2 个文件 + 发版 | 写扩展 + 发布 APK | 写解析器 | **写一个 JSON 文件** |
| 源审核/风控 | 无 | 有官方扩展仓库 | 部分 | 签名索引 + 健康度 + 远程撤销 |
| 内置内容 | 是（大量源） | 无（依赖扩展） | 部分 | **零** |
| 本地漫画 | 支持 | 支持（有限格式） | 支持 | 图片目录 / ZIP / CBZ |
| 法律姿态 | 免责声明 + 依赖第三方站 | 明确「不含内容」 | 同左 | **规则与内容彻底分离 + 投诉下架通道** |
| UI 技术 | Java + XML | Kotlin + Compose | Kotlin + Compose | **Kotlin + Compose（单语言）** |

差异化的三条护城河：

1. **规则引擎的表达力**：声明式选择器覆盖 ~80% 站点；剩余 20% 用受限 JS 钩子（解密、拼接、二次请求），而不是让作者去写 Kotlin。
2. **源的可治理性**：规则带版本、哈希、最小引擎版本、签名；引擎支持 `revoked` 列表，可对恶意/侵权规则做远程失效。
3. **纯本地数据面**：没有任何服务端依赖，项目不会因「服务器关停」而猝死。

## 5. 设计原则

1. **内容零接触**：任何「帮用户找到资源」的产品化功能（排行榜、推荐、搜索建议词）都不做；搜索框只做输入法与历史。
2. **失败要可解释**：源失效必须告诉用户是哪一步失败（请求/解析/图片），并给出可操作的下一步（改规则/换源/报 issue）。
3. **阅读优先**：任何设置项都不能以牺牲翻页流畅度为代价；UI 动画不阻塞图片加载。
4. **数据可带走**：备份是纯 JSON + 标准 ZIP，不加密、不锁定（凭据除外）。
5. **默认安全**：规则默认无文件/设备权限，网络域名白名单；危险能力显式声明并在导入时提示。
6. **数据优于代码**：能用规则表达的不写代码，能热更新的不发版；代码只保留引擎与体验，避免把源逻辑重新写回 App。

## 6. 成功度量

开源项目不追 DAU，用可观测的工程质量与社区健康度衡量：

| 指标 | 目标 | 采集方式 |
| --- | --- | --- |
| 单源搜索成功率（规则作者自测集） | ≥ 90% | CI 中的 golden fixture + 规则包作者回填 |
| 冷启动到书架可交互（中端机） | ≤ 1.5s | Macrobenchmark |
| 翻页首帧延迟（已缓存） | ≤ 100ms | 自建埋点（本地日志，不上传） |
| 阅读崩溃率 | < 0.5% 会话 | 本地崩溃日志 + 用户主动上报 |
| 规则包从提交到可用 | ≤ 24h | 索引 CI + 审核 SLA |
| Issue 首次响应 | ≤ 72h | GitHub 指标 |

## 7. 与 Cimoc 的关系（重要）

- **参考的是产品形态**：双阅读模式、源管理页、下载队列、本地阅读、备份。这些是公开可见的交互设计，不构成代码复制。
- **不复制代码**：Cimoc 为 GPL-3.0，本项目同样选择 GPL-3.0 以避免许可证冲突；但仍执行「净室实现」——只参考 `Parser` 接口的**能力集合**（搜索/详情/章节/图片/检查更新/分类），具体抽象由本项目重新设计为数据驱动的 `SourceRule` + `RuleEngine`。
- **不复制源实现**：Cimoc 的 `source/*.java` 含具体站点逻辑，一律不引入；这也正是我们要用规则包替代的部分。
- 如未来需要移植个别通用工具（如 SAF 文件树封装），必须在 PR 中标注来源、作者与许可证，并保留版权头。
